# Observability and the Four Golden Signals

This document describes the measurement layer used to test hypotheses H1–H8: the
[Google SRE Four Golden Signals](https://sre.google/sre-book/monitoring-distributed-systems/)
(latency, traffic, errors, saturation), the SLO contract, campaign telemetry and
annotations, and the alerting rules that turn a run into pass/caveat evidence.

All measurement is live. Nothing here is synthetic, and a missing series is treated
as **unknown**, never as a passing value.

## Stack

`docker compose up` starts the usual application services plus these observability
services:

| Service | Port (default) | Purpose |
|---|---|---|
| Grafana | 3000 | Dashboards, provisioned read-only |
| Prometheus | 9090 | Metrics, remote-write receiver, rule evaluation |
| Pushgateway | 9091 | Campaign phase/context/SLO/probe gauges |
| cAdvisor | — | Per-container CPU, memory, throttling, OOM |
| node-exporter | — | Host CPU and memory |
| nginx-prometheus-exporter | — | Gateway connections and accept pressure |
| postgres-exporter | — | Connections, locks, settings |
| redis-exporter ×2 | — | Redis memory, evictions, blocked clients, CPU |

Prometheus runs with `--web.enable-remote-write-receiver` and
`--enable-feature=native-histograms`, so k6 pushes native histograms directly for
windowed latency quantiles. Scrape interval is 5s; the campaign job is scraped every 2s.

Prometheus retention is pinned to a named volume (`prometheusdata`) so time series
survive a stack restart. Panel links in reports point at that window.

## Dashboard

Dashboard **OrderFlow — Four Golden Signals** (`infra/grafana/dashboards/golden-signals.json`,
uid `orderflow-golden`) is generated by `scripts/build_dashboard.py`; edit the
generator, then run it. A unit test asserts the checked-in JSON equals the generator
output.

Rows:

1. **Experiment context** — which experiment/hypotheses/strategy is active, current
   phase, telemetry completeness, configured workload, and the normal/degraded SLO
   contracts. Run identifiers live in annotations and reports, never as metric
   labels, to keep cardinality bounded.
2. **Latency** — success-only percentiles for reads and writes, failure latency,
   DB operation time, Redis command time, follower polling, and the k6 client window
   p95/p99 (native histograms).
3. **Traffic** — offered vs achieved vs successful requests, per-operation/outcome and
   per-replica traffic, cache hits by layer, DB loader origins, Redis command rate,
   dropped iterations, and achieved/offered ratio.
4. **Errors** — unexpected HTTP error ratio against the SLO, errors by operation,
   expected 409 order conflicts shown separately, Redis failures/timeouts, DB errors
   and pool-acquisition timeouts, fallbacks to PostgreSQL, invalidation/SET failures,
   and the fault/recovery-phase error ratio.
5. **Saturation** — container CPU vs quota, CFS throttling, memory vs finite limit,
   OOM events, DB pool used/limit, connection-acquisition wait, PostgreSQL
   connections/locks, Redis memory vs maxmemory, evictions/blocked clients, gateway
   connection pressure, generator VUs/CPU, and host CPU/memory.
6. **H1–H8 drill-downs** — DB SQL attempts and snapshot-load ratio (H1–H4), freshness
   observations from the last E17 probe (H4/H7), Redis availability/lock outcomes/refill
   amplification (H5–H6), and L1/L2 misses, per-shard request share, and Redis CPU (H7–H8).

A few deliberate measurement conventions:

- Latency percentiles are computed **after summing histogram buckets across replicas**;
  percentiles of per-replica averages would be wrong.
- Successful, unexpected-error, and expected-409 order traffic are distinct; the error
  ratio excludes health probes and expected order conflicts.
- The panel no-value text is `Unknown / no samples`, not zero.
- Controllers without a finite quota/limit are omitted from ratio panels rather than
  drawn as 0%.

## SLO contract

`benchmarks/slo.json` is the single source of decision thresholds:

```json
{
  "normal":   {"p95_seconds": 0.1, "p99_seconds": 0.25, "error_ratio": 0.01, "drop_ratio": 0.01},
  "degraded": {"p95_seconds": 0.5, "p99_seconds": 1.0,  "error_ratio": 0.05, "drop_ratio": 0.05},
  "recovery_seconds": 30,
  "freshness_seconds": { "db": 0, "aside": 33, "invalidate": 1, "write_through": 1,
                         "protected": 1, "l1l2": 3, "sharded": 1 }
}
```

These are **provisional laboratory thresholds**, consistent with `docs/POC_CANVAS.md`,
and must be agreed before an assessment. The `degraded` contract describes acceptable
service while a cache dependency is down but PostgreSQL still has headroom. The file
is validated at load time (positive, finite, ratios ≤ 1); invalid values fail the run.

The campaign publishes the contract as `orderflow_slo_*` gauges, so alert expressions
compare measured values against the configured thresholds rather than hardcoded numbers.
Override the path with `ORDERFLOW_SLO_FILE`.

## Campaign telemetry and annotations

`scripts/telemetry.py` (`RunTelemetry`) wraps every campaign run:

- Emits phase gauges `orderflow_campaign_phase{phase=...}` for `idle`, `warmup`,
  `measurement`, `fault`, `recovery`, `consistency`, plus `orderflow_campaign_info`,
  offered RPS, replica count, write/hot fraction, `orderflow_campaign_active`, and a
  heartbeat timestamp.
- Creates Grafana annotations for each phase transition and fault, tagged with the
  experiment, strategy, and hypotheses. Reports include a dashboard time-window link.
- Publishes E17/E18 probe results (`orderflow_probe_*`) including the stale fraction,
  the observation window, the last stale observation, and inventory-invariant violations.
- Runs a completeness check that verifies scrape targets, container discovery, and (when
  load is offered) k6 samples. `orderflow_telemetry_complete` is only 1 when all checks
  pass; otherwise the run is explicitly incomplete and its SLO must not be read as passing.
- Writes a JSON evidence file next to each run and records observability errors rather
  than letting a broken measurement masquerade as a healthy result.
- `scripts/hypotheses.py` turns the campaign's results plus the SLO contract into
  H1–H8 verdicts (`supported`/`refuted`/`inconclusive`) in every report and in
  `hypotheses.json`; missing data is always `inconclusive`.
- Grid profiles (E21 capacity, E22 resilience) reuse the same per-run telemetry. E22
  runs add `fault`/`recovery` phase annotations at the explicit `--fault-at` /
  `--recover-at` offsets, timed from k6's own run window rather than container startup.
  Each E22 report row also carries `fault_window_error_rate`, `outside_error_rate`, and
  `recovery_observed_seconds` parsed from the saved k6 samples (read requests only).
  For verdicts, H2 aggregates E20/E21 cells per `(strategy, rate)` using median metrics
  plus a per-repetition pass-fraction (≥ 0.8), and H5 prefers the worst E22 fault-window
  read error rate over the whole-run E10 window.

Note: `orderflow_probe_last_stale_seconds` is a **lower bound** on time-to-freshness,
not an upper bound. A short sequential probe cannot prove the freshness contract.

## Alerts

`infra/alerts.yml` (validated with `promtool`) contains recording rules plus alerts:

- Recording: `orderflow:read_p95_seconds`, `orderflow:read_p99_seconds`,
  `orderflow:unexpected_error_ratio`, `orderflow:drop_ratio`, `orderflow:dropped_rps`.
- Alerts: normal and degraded p95/p99 latency SLO, normal and degraded error SLO,
  generator drops, telemetry incomplete, campaign heartbeat lost, and scrape failure.

Phase-scoped alerts require the corresponding phase to be active and the campaign
heartbeat to be recent, so an alert cannot fire from a stale or unrelated window.
Rolling windows can straddle phase boundaries; for exact acceptance use the saved
sample timestamps, not the alert alone.

## Validating the instrumentation

With the stack up (and optionally during/after a campaign window):

```bash
# Fail if any panel query errors or a required metric is missing.
python3 scripts/check_observability.py

# Also require k6 histograms and campaign context at the given time.
python3 scripts/check_observability.py --at 1791737860 --require-load \
  --output results/observability/panels.json
```

The checker expands dashboard variables, runs every panel query against live
Prometheus, asserts required metric families (including container labels and the k6
histograms), and confirms Grafana provisioned the expected dashboard. It exits
non-zero on any failure.
